# ShadowNode OSINT Graph Audit

## Existing Graph Surfaces

- Active graph page: `app/cases/[id]/graph/page.tsx`.
- Legacy standalone graph component: `components/investigation/InvestigationGraph.tsx`; not used as the active case graph route.
- Existing active graph behavior before enhancement:
  - loads case entities from `/api/cases/[id]/graph/entities`;
  - loads case relationships from `/api/cases/[id]/graph/relationships`;
  - renders entities and relationships in React Flow;
  - creates manual entities;
  - creates manual relationships;
  - saves graph-created connections as `associated_with` relationships.

## Existing Tables Reused

- `investigation_entities`
  - Existing fields included `case_id`, `entity_type`, `name`, `description`, `aliases`, `verification_status`, `confidence_score`, `created_by`, timestamps.
- `entity_relationships`
  - Existing fields included source entity, target entity, relationship type, description, confidence, verification, creator, timestamps.
- `intelligence_sources`
  - Reused for imported/staged-result source attribution so report automation can consume sources.
- `entity_sources`
  - Reused to link imported entities to intelligence sources.
- `forensic_files`
  - Reused as the case evidence source for graph provenance links.
- `entity_positions`
  - Reused for graph node-position persistence.
- `investigation_tasks`
  - Reused by graph automation to create review tasks for unresolved graph intelligence.
- `case_updates`
  - Reused by graph automation and relationship changes through existing timeline helpers.
- `case_reports`
  - Existing report automation already loads entities, relationships, sources, observations, timeline, evidence, tasks, and notes.

## Authorization Observed And Preserved

- Entity and relationship graph APIs already use case-scoped access helpers from `lib/investigation-workspace.ts`.
- Read APIs use `requireCaseReadAccess`.
- Mutation APIs use `requireInvestigationWorkspace` plus role checks for super administrator, administrator, staff, investigator, and analyst.
- Relationship creation already verifies both source and target entities belong to the active case.
- New OSINT, provenance, position, automation, and update paths follow the same case access model.

## Evidence And Source Linkage Observed

- Evidence is stored in `forensic_files`.
- Existing report generation attaches evidence through `case_report_evidence`.
- Existing intelligence sources are loaded by the report generator from `intelligence_sources`.
- Existing entity-source links are represented by `entity_sources`.
- Relationship-source and graph-evidence links were missing; the OSINT workspace migration adds:
  - `relationship_sources`;
  - `entity_evidence`;
  - `relationship_evidence`.

## Graph Save And Layout Behavior Observed

- Before enhancement, graph node positions were generated by index on each load.
- Existing `entity_positions` table was present but not used by the active graph page.
- Enhancement reuses `entity_positions` for node drag persistence.

## Report Automation Observed

- `app/api/cases/[id]/reports/route.ts` builds a structured investigation packet for AI drafting.
- The report prompt explicitly prohibits invented facts and requires source/evidence references.
- Enhancement extends that packet with:
  - entity value/source/provenance fields;
  - relationship direction/source/client visibility fields;
  - explicit graph provenance links under `GRAPH PROVENANCE LINKS`.

## Provider Boundary

- No private or commercial OSINT provider is called.
- The current available transform is manual open-source review, which stages investigator-entered results only.
- Configured-provider lookup exists as a disabled registry entry until approved credentials/licensing are added.
- Staged results must be explicitly reviewed before import into graph entities or relationships.
